# Tile Layout Planner — заметки по домену

Одностраничный инструмент для планирования раскладки плитки (пол + стены) в
одной комнате: рисуешь контур комнаты, добавляешь дверные/оконные проёмы,
настраиваешь размер плитки/шов/тип раскладки для каждой поверхности,
получаешь расчёт (количество, площадь, переиспользование обрезков) и
печатные чертежи раскладки по каждой поверхности, плюс живой 3D-предпросмотр.

## Файлы

- `index.html` — всё: разметка/шаблон, стили приложения и весь класс
  `Component` (state + вся логика). Это единственный файл, который
  редактируется для изменения поведения приложения.
- `support.js` — фреймворк шаблонизации/рантайма ("DC"). Не редактировать,
  считать чёрным ящиком, если не крайняя необходимость.
- `room3d.js` — отдельный 3D-предпросмотр (Three.js), подгружается
  динамически. Экспортирует `window.createRoomView(el) -> { update(data) }`.
  Ничего не знает о состоянии приложения, кроме того, что ему передаёт
  `push3d()` на каждом рендере.
- Сборки нет. `index.html` открывается напрямую или отдаётся статикой.

## Устройство фреймворка (support.js / "DC")

- `<x-dc>...</x-dc>` внутри body содержит шаблон (HTML с `{{ expr }}`
  биндингами, `sc-if`, `sc-for`) — компилируется в React-дерево во время
  выполнения.
- `<script type="text/x-dc" data-dc-script>` содержит `class Component
  extends DCLogic { state = {...}; renderVals() {...} ...методы }`.
  `renderVals()` возвращает плоский объект, из которого читают биндинги
  `{{ }}` в шаблоне; пересчитывается на каждом рендере.
- Статический текст интерфейса **не** шаблонизирован. Паттерн: русский текст
  — это буквальный `textContent` элемента, английский лежит в атрибуте
  `data-en="..."`. `applyLang(lang)` делает ручной проход
  `querySelectorAll('[data-en]')`, который подменяет `textContent` напрямую
  (императивно, вне React). Флаг `en` в `renderVals()` — отдельная вещь,
  только для вычисляемых/динамических строк (спецификации, счётчики,
  подсказки), которые обязаны реагировать на state через обычные биндинги.
  **При добавлении новой статической подписи следуй паттерну `data-en`; при
  добавлении вычисляемой строки используй флаг `en` с тернарником — это два
  разных механизма, взаимозаменять их нельзя.**
- `style-hover="..."` на любом элементе генерирует scoped CSS-правило
  `:hover` из этой **буквальной** строки атрибута — она не проходит через
  разрешение `{{ }}` биндингов, поэтому её нельзя забиндить по-разному для
  каждого элемента внутри `sc-for`. Чтобы менять hover-поведение по
  элементам (например, отключать его), управляй этим через собственный
  базовый `style` элемента (например, `pointer-events: none` также подавляет
  `:hover`), а не через `style-hover`.
- Для быстрого тестирования/отладки на уровне DOM живой инстанс `Component`
  достижим, если пройти вверх от React-fiber любого DOM-узла
  (`el[__reactFiber$...]`) до `stateNode`, у которого есть
  `__setLogicState`, и затем прочитать `.logic`. Удобно использовать в
  консоли браузера или в скрипте автоматизации, чтобы вызывать методы /
  читать `state` напрямую.

## Модель домена

- **Контур комнаты** — `state.poly`: массив точек `[x, y]` (мм), образует
  замкнутый полигон, рёбра — это стены по порядку. `state.ops`: массив
  проёмов `{kind: 'win'|'door', wall: индексРебра, id, off, w, sill, h}` —
  `off`/`w` вдоль стены, `sill`/`h` по вертикали (от пола). Один проём на
  стену — это ограничение UI (контекстное меню скрывает пункт "добавить",
  если у стены уже есть проём).
- **Стены — производная величина, не хранятся напрямую** — `room()`
  проходит по рёбрам `poly` и вычисляет `{n: буква, edge: индекс, a, b, len,
  op}` для каждой стены. Буквы берутся из `LETTERS =
  'ABCDEFGHIJKLMNOPQRSTUVWXYZ'` (после 26-й — откат на `'W'+(n+1)`). Рёбра
  короче 10мм отбрасываются (вырожденные). `wallKey(edge)`/`edgeForWallKey(key)`
  — прямое и обратное преобразование индекс↔буква, используй их вместо
  ручного `LETTERS[edge] || 'W'+(edge+1)`.
- **Буква стены — это позиция, не идентичность.** `wallLocks` хранится по
  букве, а буква пересчитывается из индекса ребра на каждом рендере. Когда
  `addNode`/`removeNode` меняют число вершин полигона, все рёбра после точки
  вставки/удаления сдвигаются по индексу (как `shiftOps` сдвигает `ops`) —
  без аналогичного сдвига ключей `wallLocks` физический замок молча
  "перепрыгивал" на другую стену, оказавшуюся на том же индексе/букве, а
  реально заблокированная стена (теперь под другой буквой) тихо
  разблокировывалась. Это был реальный баг (исправлен): `addNode`/`removeNode`
  теперь вызывают `shiftWallLocks(at, delta)` с теми же аргументами, что и
  `shiftOps`, — замок остаётся на физической стене, даже если её буква
  меняется (это ожидаемо и нормально).
- **Координаты**: план комнаты и пол — вид сверху, y растёт "вниз", как в
  экранных координатах. **Стены хранятся от пола вверх** (y=0 — пол), но
  *отрисовываются* от потолка вниз в UI/печатных чертежах — поэтому при
  рисовании стены координата y инвертируется (`y → H − y`); вся геометрия
  раскладки (проёмы, `layoutTiles`, `holeRects`) всегда работает в
  исходной конвенции "от пола", никогда в перевёрнутой отрисовочной. Путаница
  между ними — регулярный источник багов; перед написанием нового кода по
  геометрии стен уточняй, в какой именно "y" ты находишься.
- **Настройки плитки** для каждой поверхности (`state.floor`, `state.wall`):
  `{w, h, j, type}` — ширина и высота плитки, ширина шва, тип алгоритма
  раскладки (`'classic' | 'village' | 'basic'`). Поля толщины нет — оно было
  убрано; кроме косметической подписи, толщина ни на что не влияла (не
  влияет на раскладку, площадь или расчёт стоимости), поэтому не
  восстанавливай его без реальной причины.
- **Высота комнаты** — `state.roomH`, одно значение на всю комнату (мм).

## Алгоритм раскладки плитки

- `axisSegments(type, size, t, joint)` — одна ось (ширина или высота) одной
  поверхности, возвращает размеры сегментов:
  - `classic`: целые плитки по центру, всегда резервируется запас в одну
    плитку, чтобы оба краевых обреза не были совсем узкой полоской (обычно
    получается от половины до целой плитки).
  - `village`: та же центровка, но без резервного запаса — если поверхность
    делится без остатка, обрезных плиток вообще нет.
  - `basic`: без центровки, целые плитки укладываются с одного края, один
    обрезок забирает остаток с другого края.
- `layoutTiles(...)` строит 2D-сетку (столбцы × строки) из `axisSegments`
  (либо из `manualCols`/`manualRows`, если поверхность заблокирована — см.
  ниже), обрезает каждую ячейку через переданный вызывающей стороной
  `clip(x,y,w,h)` (обрезка по контуру комнаты для пола, вырезание отверстия
  для стен) и отслеживает переиспользование обрезков.
- **Пул переиспользования обрезков** (`state.pool`, протаскивается через
  `layoutTiles`, общий для всех стен — кусок, обрезанный на стене A, может
  быть переиспользован на стене C): когда фактическая обрезанная площадь
  ячейки меньше целой плитки, сначала пытаемся взять (`take()`) из пула
  подходящий по размеру или больший прямоугольник; если такого нет — режем
  новую плитку. В обоих случаях остаток (больший из двух полосок, которые
  оставляет прямой разрез) отдаётся (`give()`) обратно в пул — **в том числе
  когда резали не свежую плитку, а уже взятый из пула обрезок**
  (`giveRemainderOf`): если взятый кусок оказался больше, чем нужно, разница
  возвращается в пул с тем же `id` и может быть переиспользована снова. То
  есть переиспользование рекурсивное — один и тот же кусок может пройти
  через `take`/`give` сколько угодно раз подряд, пока не станет слишком мал
  (`give()` не кладёт в пул кусок с любой стороной ≤1мм). Переключается
  флагом `state.reuseOffcuts` (чекбокс «Переиспользовать обрезки» в блоке 3,
  по умолчанию включён, хранится в проекте) — при выключении `take()`
  никогда ничего не находит (каждый обрез режется из свежей плитки), но
  `give()` всё равно кладёт каждый обрезок в пул, поэтому список «Остатки»
  честно показывает вообще все обрезки, а не только невостребованные.
  **Решение "резать или не
  резать" принимается по фактической геометрии результата
  (`isAxisRectPoly` + реальный bounding box обрезки), а не просто по тому,
  стоит ли ячейка на границе сетки** — полноразмерная внутренняя ячейка
  сетки, которую подрезал проём (например, дверь с приподнятым от пола
  порогом оставляет под собой короткую полоску), точно так же годна для
  переиспользования, как и краевая ячейка, и должна проходить через
  `take`/`give` точно так же. Это был реальный баг (исправлен): раньше в
  переиспользовании участвовали только ячейки на границе сетки, поэтому
  любой обрез, вызванный проёмом на иначе целой плитке, молча не давал ни
  взятого, ни отданного обрезка. Известное оставшееся ограничение: ячейка,
  чья обрезка — *не* один прямоугольник, соосный осям (проём срезает угол →
  L-образная/шестиугольная форма, либо две несвязанные полоски выше и ниже
  проёма в пределах одной строки), всё ещё откатывается к старой эвристике
  "только по границе сетки" — на практике редкость, не стоит усложнения,
  если не всплывёт снова.
- Список «Остатки» (блок 3) группирует обрезки по **точному** `w×h`
  (округлённому до мм), а не только по площади — так каждая строка гарантированно
  соответствует одному конкретному размеру, а не двум случайно совпавшим по
  площади разным прямоугольникам. Это оправдано тем, что `give()` всегда
  кладёт в пул именно `{w,h}`-прямоугольник (см. выше), даже если реально
  установленный кусок был неровным — модель остатка всегда прямоугольная.
  Наведение на строку показывает всплывающий чертёж куска с размерами,
  переиспользуя тот же механизм, что и наведение на переиспользованную
  плитку в чертежах блока 4: `setDimHover(poly, rect)` → `state.dimHover` →
  `tileDimSvg(poly)`; для строки остатка просто передаётся синтетический
  прямоугольный `poly` `[[0,0],[w,0],[w,h],[0,h]]`.
- `holeRects(cell, ops)` — вырезает один проём стены из одной ячейки сетки.
  Точно обрабатывает только ≤1 проём (стена через UI получает не больше
  одного); ≥2 откатывается на `subtract()` + `mergeRects()` (независимые
  гильотинные разрезы, может оставить лишний видимый стык там, где
  встречаются два разреза — приемлемо, так как через UI недостижимо).
- `clipPoly` (алгоритм Сазерленда — Ходжмана) обрезает сетку пола по
  реальному (возможно, не прямоугольному) полигону комнаты.

## Ручной редактор раскладки и блокировки

- В блоке 4 ("Чертежи раскладки") у каждой поверхности есть иконка
  карандаша, открывающая полноэкранный редактор (`state.layoutEditor =
  {kind: 'wall'|'floor', key, edge, cols, rows}`), где можно тащить швы.
- Перетаскивание шва (`startEditJointDrag` → `resolveRegion`): *регион*
  между двумя соседними фиксированными швами перепаковывается со стороны,
  которая растёт, целыми сегментами размера плитки, пока не понадобится
  разделение (сегмент превысил бы настроенный размер плитки → появляется
  новый шов), а сжимающаяся сторона остаётся одним сегментом, пока не
  схлопнется почти до нуля (`EPS`) и не будет отброшена целиком. Прилипает
  к точной середине между двумя фиксированными соседями, если рядом
  (`mid = (regionLen − joint) / 2` — **не** `regionLen / 2`, из-за чего две
  стороны отличались бы ровно на ширину шва), и к краям проёма при
  перетаскивании рядом с ними (`OPEN_SNAP`). Прилипание к проёму нацелено
  на `edge − joint/2`, а не на сам `edge` — снап должен сажать на границу
  проёма **центр** шва (половина шва видна у стены, половина «съедена»
  проёмом), а не его край (иначе весь шов целиком проваливается внутрь
  проёма и становится невидимым, что при толстом шве выглядит как «прилип
  где-то сбоку»); плюс прилипание к проёму приоритетнее прилипания к
  середине региона — если оба варианта близко, побеждает проём
  (`skipMidSnap` в `resolveRegion`), а не наоборот. Перетаскиваемый шов
  берётся за свой **отрисованный центр**, но все дальнейшие координаты
  (`mouseLocal`, края проёма) — это координата *края* плитки; перед
  использованием нужно вычесть `joint/2` из исходной позиции курсора,
  иначе толстый шов при простом захвате незаметно "съезжает". Сумма
  сегментов, которые возвращает `resolveRegion` (с учётом швов МЕЖДУ
  ними — `sum(segs) + (segs.length-1)*joint`), всегда должна точно
  равняться `regionLen` — это ломалось уже трижды: пропущенное `- joint`
  на дальней стороне, случай слияния в последний сегмент, и третий раз —
  `Math.max(0, rightRem)` в ветке слияния молча отбрасывал отрицательный
  `rightRem`, из-за чего утаскивание шва вправо ПОСЛЕ того, как он уже
  слился с соседним, продолжало прибавлять до целого `joint` к последней
  плитке (и сдвигало всё, что после неё, в массиве) вместо того, чтобы
  оставаться на месте — `joint + rightRem` без клампа корректен при любом
  знаке `rightRem`. Любое изменение здесь стоит перепроверять именно на
  точность этой суммы, а не только глазами на паре примеров.
- **Блокировка** (`state.wallLocks[буква]`, `state.floorLock`) замораживает
  текущие cols/rows поверхности, чтобы алгоритм classic/village/basic
  перестал их пересчитывать. Зона действия блокировки *стены*: поле "Длина"
  (блок 1), поля её проёма (блок 1), **глобальные** настройки плитки стен в
  блоке 3 для *всех* стен (`anyWallLocked()` — одна заблокированная стена
  полностью выводит общие настройки из игры), перетаскивание этой стены,
  прилегающих к ней узлов или её проёма вдоль стены (`startOpDrag`), и —
  важно — **добавление/удаление узла или проёма на этой стене**
  (`addNode`/`removeNode`/`addOp`/`removeOp` все проверяют `isWallLocked`,
  поскольку любое из этих действий сделало бы замороженную раскладку
  недействительной). Контекстное меню по правому
  клику это тоже отражает: заблокированная стена (или узел на её границе,
  или её проём) показывает неактивную строку "эта стена заблокирована"
  вместо обычных действий. Блокировка *пола* отключает только настройки
  плитки пола в блоке 3 — она не блокирует редактирование формы комнаты (у
  пола нет аналога "длины стены").

## Персистентность

- **Проекты**: `localStorage['tileLayoutProjects']` — массив полных снапшотов
  (`projectSnapshot()`: poly, ops, roomH, floor, wall, wallLocks, floorLock +
  id/name/version/savedAt). Всё остальное (количество плиток, списки
  обрезков, итоги) пересчитывается заново в `renderVals()`, никогда не
  сохраняется. `localStorage['tileLayoutCurrentProjectId']` указывает на
  активный проект. `normalizeProjectData()` проверяет только форму (нужные
  типы/ключи присутствуют), а не корректность полей — поэтому убрать/добавить
  поле в `floor`/`wall` можно без миграции, старые сохранённые объекты просто
  навсегда носят с собой лишние (безвредные) ключи. **`componentDidUpdate`
  автосохраняет при каждом `setState`** — отдельного шага "сохранить" нет.
  Это важно для ручного тестирования: вызов `logic.setState(...)` из devtools
  на реально загруженном проекте немедленно перезапишет его в `localStorage`.
  Для тестирования алгоритмов предпочтительнее вызывать чистые методы
  напрямую (`layoutTiles`, `wallTiles`, `resolveRegion`, `axisSegments`);
  если без `setState` на реальном проекте не обойтись — сначала сохрани
  исходные поля и восстанови их после.
- **Настройки редактора** (тема, язык) хранятся отдельно:
  `localStorage['tileLayoutEditorPrefs']`, читаются синхронно в `state` до
  первой отрисовки (чтобы не мигала неправильная тема/язык).
- **Undo/redo**: `pushHistory()` (вызывать перед любым изменением) сохраняет
  снапшот `{poly, ops, roomH, floor, wall, wallLocks, floorLock}`;
  `undo`/`redo` снимают его со стека. Ctrl/Cmd+Z работает глобально, кроме
  случая, когда в фокусе текстовое поле (чтобы работал нативный undo поля).
  **Ручной редактор раскладки (`state.layoutEditor`) имеет полностью
  отдельный стек** — `layoutEditorHistPast`/`Future`, `pushLayoutEditorHistory`/
  `undoLayoutEditor`/`redoLayoutEditor`, снимок — только `{cols, rows}`.
  Пока редактор открыт, глобальный обработчик Ctrl+Z/Ctrl+Shift+Z (в
  `onKeyDown`) целиком переключается на этот стек вместо основного —
  иначе отмена во время открытого редактора откатывала бы случайное более
  раннее изменение комнаты под лежащим сверху модальным окном. Снимок
  делается один раз в начале каждого перетаскивания шва
  (`startEditJointDrag`, до первого `pointermove`), а не на каждый кадр
  движения. Стек сбрасывается (`clearLayoutEditorHistory`) при каждом
  открытии редактора (`openLayoutEditor`); при закрытии/сохранении
  специально ничего не делает — черновик редактора одноразовый.

## Тема оформления

- CSS custom properties; **`:root` содержит значения тёмной темы** (это
  базовые значения), `:root[data-theme="light"]` их переопределяет для
  светлой — то есть тёмная тема является дефолтом/фолбэком, а не светлая.
  Отдельный блок `@media print` принудительно задаёт фиксированную
  чёрно-бело-серую палитру независимо от `data-theme` (`--color-text`/
  `--color-accent`/`--c-tile-line` → чёрный, `--c-tile` → светло-серый,
  `--c-tile-cut` → заметно темнее `--c-tile`, а не просто другой оттенок —
  два похожих по светлоте цвета сливаются в один серый после того, как
  драйвер принтера обесцвечивает страницу, стирая различие между целой и
  резаной плиткой на бумаге). **Гочка со специфичностью**: правило нужно
  писать как `:root, :root[data-theme="dark"], :root[data-theme="light"]`
  — перечисление и тёмного, и светлого атрибютного селектора обязательно,
  не для симметрии: у обычного (не print) правила `:root[data-theme="light"]`
  специфичность выше, чем у голого `:root`, поэтому без явного
  `:root[data-theme="light"]` в print-блоке печать в светлой теме тихо
  использовала бы обычные (не серые) цвета светлой темы. В печать также
  идут только чертежи из блока 4 — сам заголовок блока 4 (бейдж/заголовок/
  описание) помечен `data-noprint`, поскольку это чисто экранная навигация,
  а не часть чертежа.
- Переменные `--c-3d-*` питают материалы 3D-вида через `push3d()`, читающий
  `getComputedStyle` — то есть изменение цвета в 3D — это правка CSS
  переменной, а не правка room3d.js. `--c-3d-bg` намеренно светло-серый в
  тёмной теме (а не почти белый, как в светлой) — конкретно для того, чтобы
  3D-вьюпорт не светился как ослепительно белый прямоугольник на фоне
  остального тёмного интерфейса, при этом швы остаются видимыми на фоне
  плитки.

## Интеграция 3D-вида

- `this.last` (room, floorPolys, wallPolys) присваивается как побочный
  эффект **внутри `renderVals()`** — намеренно нечисто, поскольку 3D-виду
  нужна та же самая вычисленная геометрия, которую только что произвёл
  2D-рендер, без повторного пересчёта. `push3d()` (вызывается из
  `componentDidUpdate`) читает `this.last` и передаёт снимок обычных данных
  в `this.view.update()`. При рефакторинге `renderVals()` сохраняй
  присвоение `this.last` той же формы — иначе 3D-вид молча устареет/станет
  пустым.

## Заметки по тестированию (для проверки через браузерную автоматизацию)

- Получить живой инстанс логики через обход fiber, описанный выше, удобно
  сохранить в `window.__tlLogic`.
- Для проверки чистых алгоритмов (прилипание, обрезка, переиспользование)
  вызывай `logic.resolveRegion(...)`, `logic.layoutTiles(...)`,
  `logic.wallTiles(...)`, `logic.axisSegments(...)`, `logic.holeRects(...)`
  напрямую — без `setState`, без риска для персистентности, с точными
  входами/выходами.
- Для проверок на уровне UI (перетаскивание, прилипание через реальные
  события указателя) вычисляй целевые координаты через `getScreenCTM()`
  соответствующего `<svg>` (прямое преобразование в экранные координаты для
  синтетического `PointerEvent`, обратное — как это делает сам `toUser()`
  для чтения), а не угадывай пиксели по скриншотам — гораздо точнее и
  воспроизводимо.
- Следи за **устаревшим состоянием блокировки** реального проекта при
  построении тестовых сценариев (например, вызов `wallTiles(..., 'A')` на
  проекте, где стена A случайно заблокирована, молча подставит
  заблокированные ручные cols/rows вместо той сетки, которую ты думал, что
  тестируешь — используй для синтетической геометрии букву стены без
  блокировки, например `'Q'`).
- Одно сообщение в консоли всегда присутствует и его всегда можно
  игнорировать: "A listener indicated an asynchronous response by returning
  true, but the message channel closed..." — артефакт расширения Chrome, не
  ошибка приложения.
